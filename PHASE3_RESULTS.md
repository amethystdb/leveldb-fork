# Track A: stock-vs-adaptive metrics under REAL tiering (post-Phase 3)

Generated by `amethyst_bench.cc` (repo root) at commit `a0e9483` (descendant of
`cc6202c`, the Phase 3 real-tiered-compaction landing). "stock" = this fork
with `adaptive_enabled=false`; "adaptive" = same binary with
`adaptive_enabled=true`. Unlike Phase 2, tiering here is confirmed **REAL**
(`overlap_check` verdict: REAL, genuine overlapping L1 runs observed both
during writes and at settle) — this table supersedes Phase 2's, where every
number was explicitly preliminary because no file ever accumulated a real
overlapping run.

## Config

`filter_policy=nullptr`, `compression=kNoCompression`, `write_buffer_size=1MB`,
`max_file_size=512KB`, `tiered_batch_merge_run_threshold=4` (default),
`adaptive_poll_interval_ms=2500` (default), single machine, no other load
quiesced beyond normal desktop background processes.

## Metric definitions — FROZEN for Track B

Unchanged in semantics from Phase 2 (`ws-impl/amethyst` Go prototype
definitions). **Track B's parameter sweep (`tiered_batch_merge_run_threshold`,
`adaptive_poll_interval_ms`) inherits these exact definitions — do not change
them.** Full derivations are in `PHASE2_RESULTS.md`; summary:

- **WA** = `leveldb.bytes-written` (flush + compaction bytes) / user bytes
  (every `Put`'s key+value size, non-deduplicated).
- **RA** = sum, per `Get`, of "files across all levels whose user-key range
  contains the queried key" / total `Get`s — a live metadata range-overlap
  count (matches `GetSegmentsForKey`), not "files actually opened via I/O."
- **SA** = on-disk `.ldb` bytes / logical live bytes. **Reclamation caveat
  still applies** (this fork eagerly deletes obsolete files, unlike the Go
  prototype's never-reclaim path — not comparable across engines with
  different reclamation regimes). **New expectation as of Phase 3: SA is
  expected to be measurably higher under adaptive than stock** — L1 now
  genuinely holds overlapping accumulated runs before batch-merging, trading
  space for reduced write-amp. This shows up below (overwrite: 4.821 vs
  4.555) and is the correct cost of tiering, not an instrumentation bug.
- **Throughput** = ops/sec from the workload driver. Corroborating only, not
  headline — deterministic vs. thermally-noisy (see "What these numbers show").
- **Transitions** (new in Track A) = lifetime `tiered_to_leveled` /
  `leveled_to_tiered` switch counts actually triggered by
  `AdaptiveController::ShouldRewrite`, exposed via the new
  `leveldb.adaptive-transitions` property. Printed in every row so a WA/RA
  difference can be attributed to the adaptive mechanism actually firing,
  not just the always-on tiered-read-path overhead.

`updaterandom` is a RocksDB-only benchmark name; confirmed absent from
`amethyst_bench.cc`'s workload set (`{fillrandom, readrandom, overwrite,
shifting}` — anything else is a hard CLI error, not a silent no-op).

## Repeat protocol

Deterministic metrics (WA/RA/SA/transitions): 5 repeats per (workload, mode).
Throughput: same 5 runs, median [min–max] reported. **Two combinations failed
the identical-across-repeats check** — both investigated and root-caused
below rather than averaged away, per the standing instruction that
non-reproducibility is itself a finding.

## What these numbers actually show

- **Zero transitions everywhere, again.** As in Phase 2, no run of any
  workload crossed the adaptive controller's promotion/demotion thresholds
  (`read_trend > 0.3 && readCount > 500`, `write_trend > 0.3 && writeCount >
  10`) even once. Per the standing interpretation rule, this is a valid,
  reportable result, not a failed run: **REAL tiering is confirmed working
  (`overlap_check` = REAL) and reads remain correct through it (`diff_fuzz`
  PASS, `DBTest.RandomizedWithAdaptiveEnabled` green), but under these
  workload configurations the controller's promotion threshold was never
  crossed, so aggregate WA/RA show no adaptive-*switching* effect** —
  consistent with the known per-file-number counter-reset limitation
  (history re-seeds on every compaction) and the just-landed warm-up-guard
  fix (`kMinWindowsForSwitch=4`) making an early, spurious switch even less
  likely. The WA/SA differences that *do* show up below come entirely from
  Phase 3's accumulate/batch-merge mechanism itself (which runs independently
  of `ShouldRewrite`), not from any strategy switch.
- **overwrite: SA is measurably higher under adaptive (4.821 vs 4.555), WA
  slightly higher too (1.171 vs 1.141).** This is the expected Phase 3 cost
  of real tiering flagged above: L1 holds accumulated overlapping runs
  (`tiered=4` vs stock's `tiered=3` at settle) before batch-merging, so more
  live data is held at once. Small keyspace (3,000 keys) keeps this modest in
  absolute terms, but the direction is exactly the predicted trade — this is
  not a bug.
- **fillrandom/adaptive's WA and SA are NOT reproducible across 5 repeats**
  (WA 2.923–3.216, SA 1.013–1.174, tiered-file count 11–13 at settle) —
  investigated rather than averaged. Diagnosis: a scratch-patched build that
  kept re-reading WA for 8s after `SettleCompaction()` returns showed each
  individual run is internally stable (flat for the full 8s) — so this is
  **not** a premature-settle artifact. The final *converged* state itself
  genuinely differs run to run. Root cause: `tiered_batch_merge_run_threshold`
  (the only batch-merge trigger in this cut — no size-based trigger) is a
  **run-count** threshold, and whether a given L0→L1 flush becomes "the 4th
  accumulated run" (triggering an immediate flatten to L2) or stays "the 3rd"
  depends on the real-time interleaving of the background compaction thread
  against the foreground write loop — genuine OS-scheduling nondeterminism,
  not a function of the logical (fixed-seed) `Put` sequence. Ordinary stock
  LevelDB compaction is confluent (same final sorted state regardless of
  scheduling order), so it doesn't have this problem — count-triggered
  accumulate/batch-merge is not confluent, since crossing the threshold
  earlier vs. later leads to materially different total compaction work from
  then on. `overwrite` and `shifting` don't expose this because their small
  keyspaces (3,000 / 5,000 keys) only ever produce 3–4 tiered files total,
  giving little room to hover near a threshold crossing more than once;
  fillrandom's 100k-keyspace run produces enough L1 files (11–13) to cross
  the threshold multiple times, giving scheduling jitter repeated chances to
  tip the outcome. **This is a legitimate, mechanistically-understood
  limitation of the current run-count-only trigger design** (already flagged
  as the only trigger in this cut), not a workload-tuning artifact — reported
  as a range per the user's explicit direction, not averaged into a single
  misleading number.
- **readrandom/stock's RA and SA are also not fully reproducible across 5
  repeats** (RA 1.000–1.071 stable-ish; SA is 1.013 in 4 of 5 runs but 2.078
  in one) — found while investigating the above and worth flagging since it
  affects **stock mode**, not just adaptive. Root cause: this is stock
  LevelDB's own pre-existing, unmodified seek-compaction heuristic
  (`Version::UpdateStats`/`allowed_seeks`, `version_set.cc:530-536` —
  untouched by Amethyst), which schedules a compaction once a file's
  `allowed_seeks` budget (`max(100, file_size/16384)`) is exhausted by reads
  that had to check it after another level was already checked first. With
  ~11-13 files spread across levels for a 100k-key readrandom pass, this can
  fire mid-read-phase in some runs and not others depending on whether the
  resulting compaction completes before the final property read — the one
  outlier run (SA 2.078) is exactly that: a seek-compaction actually
  completed and changed on-disk layout before measurement. This is **not**
  Amethyst-specific and predates this fork entirely; noted here because it
  directly affects how noisy stock-mode RA/SA can be in a read-heavy
  benchmark, independent of anything the adaptive controller does.
- **Throughput has substantial run-to-run variance** on this machine, as
  already known from Phase 2 (a prior ad hoc rerun swung 132k→6.5k reads/s
  with zero code change) — the widest spread here is readrandom/adaptive
  (97,872–219,444 reads/s). This is exactly why throughput is corroborating
  only: unlike WA/RA/SA/transitions, it has no exact-repeat guarantee even in
  principle, so no single number from it should be treated as a finding.
- **No workload shows adaptive beating stock on WA/RA by a margin that would
  be a "red flag" result** (per the standing rule that a large adaptive win
  is a bug, not a triumph) — the two unstable cases above are read as
  measurement/scheduling noise with a known mechanism, not an adaptive
  advantage, since transitions=0 rules out the adaptive-switching path as the
  cause in both.

## Track B handoff

`adaptive_enabled`, `tiered_batch_merge_run_threshold`, and
`adaptive_poll_interval_ms` are all `Options` fields, read (not hardcoded)
at every call site that matters:
`version_set.cc:110` (`LevelAllowsTieredAccumulation`), `:1214`, `:1564`,
`:1739` (batch-merge threshold checks), `:1505` (adaptive block gate),
`db_impl.cc:727` (poll interval), `db_impl.cc:1734` (poll-thread spawn gate).
No mechanism code hardcodes a bypass of any of these three. Track B can drive
its sweep purely by varying `Options` and rerunning `amethyst_bench` — the
metric-measurement code (`WritePhase`, `TimedReadPhase`, `MeasureRA`,
`DirLdbBytes`, `GetBytesWritten`, `GetTransitionCounts`) needs zero changes.
One caveat: `MakeOptions()` in `amethyst_bench.cc` currently only exposes
`adaptive_enabled` as a CLI argument — Track B will need to add trivial CLI
plumbing (or a recompiled constant) to actually vary the other two fields
per sweep point; "zero harness changes" applies to the measurement logic,
not to argument parsing for the new sweep dimensions.

## Parity verification (adaptive_enabled=false ≡ stock)

Re-verified at this commit (the Phase 2 worktree wasn't preserved, so this
recreates it): `parity_workload.cc` run against this fork with
`-DLEVELDB_AMETHYST` (`adaptive_enabled=false`) and against a freshly built
stock LevelDB (`main` @ `7ee830d`, same options otherwise), fixed seed
20260718, 150,000 mixed Put/Delete ops, settle-wait before close.

- Every `.ldb`, `.log`, and `CURRENT` file byte-for-byte identical (`cmp`)
  between the fork (adaptive off) and stock build.
- `MANIFEST-000002` differs, as expected and not a regression: Phase 1's
  `kFileStrategy` VersionEdit tag is unconditionally encoded regardless of
  `adaptive_enabled`, so the MANIFEST *format* itself diverges from stock
  even with the mechanism fully disabled. Phase 2's parity claim was scoped
  to `.ldb` files specifically for the same reason — the data files, which
  is what any consumer of the DB actually reads, are identical; the
  metadata-log format is a permanent, harmless divergence.

This confirms `adaptive_enabled=false` still disables the periodic poll
thread and `PickCompaction`'s adaptive-rewrite/accumulation logic completely
enough that this fork's stock-baseline mode is indistinguishable from genuine
stock LevelDB at the data level, unchanged since Phase 2.
