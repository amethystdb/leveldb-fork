# Phase 2: stock-vs-adaptive metrics

Generated by `amethyst_bench.cc` (repo root), 3 runs per (workload, mode), medians
reported. "stock" = this fork with `adaptive_enabled=false`, verified
byte-identical to a genuine stock LevelDB build (`main` @ `7ee830d`) on a fixed
seed by `parity_workload.cc` (see "Parity verification" below). "adaptive" =
same binary with `adaptive_enabled=true`.

**Every adaptive number below is preliminary — cosmetic tiering.** Phase 0/1
established that tiering is still cosmetic (`overlap_check` verdict:
COSMETIC): no file ever accumulates a genuinely overlapping run, so the
adaptive engine's compaction *decisions* are byte-identical to stock's
whenever no strategy switch fires — and across all four workloads below, none
ever did (`tiered=N leveled=0` in every run). Given that, adaptive is expected
to equal stock (mechanistically identical) or be slightly worse (linear-scan
tiered-fallback in `ForEachOverlapping`, the periodic poll thread, and the
extra MANIFEST/metadata bookkeeping all cost something with no corresponding
benefit yet). **Adaptive measuring better than stock is a signal to distrust
the measurement, not to report a win** — see the shifting-workload note below.

## Config

`filter_policy=nullptr`, `compression=kNoCompression`, `write_buffer_size=1MB`,
`max_file_size=512KB`, single machine, no other load quiesced beyond normal
desktop background processes.

## Metric definitions (matched to the Go prototype, `ws-impl/amethyst`)

- **WA** = `leveldb.bytes-written` (new GetProperty; sum of
  `DBImpl::stats_[level].bytes_written` across all levels, raw bytes) / user
  bytes (sum of key+value size over every `Put` issued, non-deduplicated).
  Confirmed against `ws-impl/amethyst/cmd/amethystd/main.go`: `physicalBytes`
  is incremented on **both** memtable flush (`sstWriter.WriteSegment` right
  after `mem.Flush()`) and compaction output — so the Go prototype's WA
  **includes the memtable→L0 flush**, and this number matches that (LevelDB's
  own `stats_[level].bytes_written` is likewise incremented in both
  `WriteLevel0Table` and `DoCompactionWork`).
- **RA** = sum, per `Get`, of "files across **all** levels whose
  `[smallest_user_key, largest_user_key]` range contains the queried key" /
  total `Get`s. This matches `GetSegmentsForKey`'s semantics exactly: that
  function returns every range-overlapping segment across the whole DB before
  any I/O happens, and the Go benchmark sums `len(segs)` regardless of how
  many the subsequent read loop actually opens. It is **not** "files actually
  touched via I/O" — our own `Version::Get` short-circuits across levels once
  it finds an answer, which would *undercount* relative to this definition.
  Measured via a dedicated untimed pass that re-parses `leveldb.sstables`
  before every read (live, matching `GetSegmentsForKey`'s per-call metadata
  query), replaying the exact key sequence used for the timed throughput
  pass so the two numbers are apples-to-apples.
- **SA** = on-disk `.ldb` bytes / logical live bytes (sum of key+value size
  for the current set of live/unique keys). **Reclamation caveat:** this
  fork's compaction path is unmodified from stock (Phase 0 verdict), so
  obsolete files are eagerly deleted exactly as in stock LevelDB — directory
  size already tracks live data closely for both stock and adaptive here.
  This will **not** remain true once Phase 3 lands real tiered accumulation
  (or if a future engine defers reclamation, as the Go prototype's
  single-append-file SA path does) — SA then becomes two different
  accounting regimes and this number stops being comparable as-is.

## What these numbers actually show

- **WA and SA are identical between stock and adaptive in every workload.**
  This is the expected, mechanistically-correct result: with zero strategy
  switches firing anywhere, the compaction path adaptive takes is the exact
  same code stock takes (Phase 1's `SetupOtherInputs` fix only changes
  *metadata inheritance*, not merge/output bytes). Identical WA/SA is
  evidence the harness and the parity claim are both sound, not evidence of
  anything interesting about adaptation.
- **RA differences (readrandom: 1.091 vs 1.044) are within same-mode noise**
  — stock's own 3 runs ranged 1.085–1.132, a wider spread than the
  stock-vs-adaptive gap. RA reflects live file-layout snapshots, and file
  layout has run-to-run timing jitter (see next point) independent of
  adaptive vs. stock; this is not a real read-amplification difference.
- **Throughput has substantial run-to-run variance** on this machine —
  a single ad hoc rerun of the shifting workload alone (not part of the
  medians above) swung from 132k to 6.5k reads/s between runs with no code
  change, purely from background-compaction-timing / OS scheduling jitter.
  The 3-run medians above are calmer but not immune to it.
- **Shifting's adaptive throughput reads ~10–15% ahead of stock across all 3
  repeats, despite identical WA/SA/RA.** Per the instruction that motivated
  this table: adaptive beating stock here is a red flag, not a result, and I
  am not reporting it as one. Since the metrics that would reflect a genuine
  behavioral difference (WA/SA/RA) are identical, there is no mechanistic
  reason for adaptive to be faster — the most likely explanation is
  measurement noise (this workload's compaction settle-timing sensitivity
  was the most visible of any workload during tuning; see the 132k/6.5k swing
  above, observed specifically on this workload). Do not cite this number as
  an adaptive win. A defensible throughput comparison needs a quieter
  machine, more repeats, and ideally warm-up runs discarded — none of which
  this preliminary pass does.
- **No promotions occurred anywhere** (`tiered=N leveled=0` in every single
  run, including every checkpoint inside the shifting workload's read-heavy
  phases). This is the **expected per-file `readCount`-reset behavior, not a
  scheduler failure**: the periodic poll (landed two commits ago) does now
  reach `PickCompaction`'s adaptive-rewrite check on a timer during
  read-only phases, so the *scheduling* gap from Phase 0 is fixed. But
  `FileMetaData::readCount` only accumulates while a specific physical file
  is alive, and any file swept into an unrelated compaction gets a **fresh**
  `FileMetaData` (and thus a reset counter) — see Phase 0's finding that
  `Compaction` output always allocates a new `FileMetaData`. Over 3 short
  read phases of 8,000 reads each against a handful of files, no single
  file's `readCount` had a realistic chance to cross the promotion threshold
  (`read_trend > 0.3 && readCount > 500`) before being rewritten by ordinary
  compaction. This is exactly what Phase 4's region-keyed counters are meant
  to fix, not a sign the poll thread isn't working.

## Parity verification (adaptive_enabled=false ≡ stock)

`parity_workload.cc`, run against this fork with `-DLEVELDB_AMETHYST`
(`options.adaptive_enabled = false`) and against a stock LevelDB build
(`main` branch, commit `7ee830d`, same options otherwise), on two different
fixed seeds (20260718, 999983), 150,000 mixed Put/Delete ops each, with a
compaction-settle wait before close (to avoid an unrelated, pre-existing
LevelDB shutdown race where `shutting_down_` can abort an in-flight
compaction mid-output on either build):

- Same `.ldb` file **names** in both output directories (proof the
  compaction schedule — which files got created, when, from what — was
  identical).
- Every `.ldb` file **byte-for-byte identical** (`cmp`) between the fork and
  stock build, on both seeds.

This confirms `adaptive_enabled=false` disables the periodic poll thread and
`PickCompaction`'s adaptive-rewrite check completely enough that this fork's
stock-baseline mode is indistinguishable from genuine stock LevelDB at the
data level, not just "no strategy switches happened to fire."
